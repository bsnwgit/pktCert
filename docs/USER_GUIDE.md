# pktCert — User Guide

This guide is for people who use pktCert to track certificates, run
discovery scans, and issue certificates day-to-day — not for installing or
administering the server. See [ADMIN_GUIDE.md](ADMIN_GUIDE.md) for setup,
users, backups, and integrations, and
[PKI-and-Discovery.md](PKI-and-Discovery.md) for a deeper look at CAs,
templates, and CSR signing.

## Logging in

Log in with your username and password, or SSO if SAML is configured.

Passwords must be at least 8 characters. After five failed attempts in a
row, sign-in is blocked for that username from your machine for a few
minutes — wait for it to clear and try again, or ask an admin to reset
your password.

| Action | Admin | Analyst | Viewer |
|---|---|---|---|
| View everything | ✓ | ✓ | ✓ |
| Manage Scan Targets, ack/resolve alerts | ✓ | ✓ | — |
| Issue/revoke certificates, manage CAs & templates | ✓ | — | — |
| Reveal a stored private key or install passcode | ✓ | — | — |
| Manage Settings, users, integrations | ✓ | — | — |

## Navigation

**Dashboard**, **Certificates**, **Scan Targets**, **Certificate
Authorities**, **Approvals**, **Alerts**, **Logs**. **Settings** appears
only for admins.

Settings has a section bar at the top with **Common** (General, Security,
Data, Notifications, User Keys, System — the same in every pkt* app) and
**pktCert** (Cert Settings, Cert Keys, Templates, Enrolment, Discovery &
Alerts). The tab row below shows one section at a time, so switch sections
if a tab looks missing.

## Dashboard

Summary tiles (total/valid/expiring/expired/revoked, CA count, enabled
scan targets, active alerts) plus two live shortcuts: certificates
expiring or already expired (soonest first), and inventory-by-status. Both
link straight into the Certificates page pre-filtered.

## Certificates

The unified inventory — every certificate pktCert knows about, regardless
of where it came from:

- **scan** — discovered by an active TLS connection to a Scan Target
- **ct** — found via Certificate Transparency log search
- **issued** — generated by one of your internal CAs
- **enrolled** — requested by a device itself over EST
- **external** — uploaded from an outside CA (purchased, Let's Encrypt, etc.)

Status is `valid`, `expiring`, `expired`, `revoked`, or `superseded` — the
last meaning it has been renewed and replaced. A superseded certificate is
still valid and still trusted; it just stops raising expiry alerts, because
the replacement it would be asking for already exists.

Filter by status, source, or search box; click a row to open its detail —
subject/issuer/SANs/serial/fingerprint, plus **View Certificate PEM** and
**View Chain PEM** (public data, no extra confirmation needed).

**Admins only:**
- **+ Issue Certificate** — pick a CA and a template, enter a Common Name
  and optional SANs. The private key is generated server-side and shown
  once immediately after issuance — copy it then, since viewing it again
  later requires re-entering your password (see below).

  Optionally tick **"Protect the private key with a passphrase"** and
  enter one twice. The exported key is then encrypted with it, so whoever
  installs it on a server has to type that passphrase. pktCert does not
  store the passphrase — if you lose it the key is unusable and the
  certificate has to be reissued. Protected keys are marked with a 🔒 on
  the issuance result and on the certificate's detail view. Leave the box
  unticked for a plain, unencrypted key.
- **+ Upload External Certificate** — for certs from an outside CA. Upload
  a PEM cert (+ optional separate key file) or a single PKCS#12 (.pfx/.p12)
  bundle, plus an optional **install/use passcode** — free text for
  whatever ops needs to know to install or use the cert (a PFX export
  password, a note, anything).
- **Revoke** — terminal; the certificate moves to `revoked` status and is
  included in its CA's next CRL.
- **Reveal Private Key** / **Reveal Passcode** — shown only if the
  certificate has one stored. Every reveal requires re-entering your
  *current* password first (a small confirmation dialog), and is logged
  for audit — this applies the same way to internally issued and
  externally uploaded certificates.

## Scan Targets

A target is a single host or a CIDR range, plus a list of ports. On its
own schedule (or immediately via **Scan Now**), pktCert connects via TLS
to every host:port pair and adds/updates whatever certificate it finds.
Status shows `ok`/`error`/`unknown` with the last error message if a scan
failed to reach anything.

## Certificate Authorities

Root CAs (self-signed) and intermediate CAs (signed by a root you
control) — expand a root to see its intermediates. **+ Add CA** offers three
routes:

- **Generate** — a new CA, key and all, created here.
- **Import** — an existing certificate and key you already have.
- **Offline Root** — register a root by its **certificate only**, keeping its
  private key somewhere pktCert can't reach. pktCert can never sign with it,
  which is the protection: whoever compromises this server still can't produce
  a certificate under your root. Use **Request Intermediate** to generate a
  signing key here plus a CSR, sign that CSR on the machine holding the root
  key, then **Import Signed Certificate**.

When generating, **Constraints** are worth opening. *Path length* caps how
many CAs may sit below this one (an intermediate defaults to 0 — it can issue
certificates but not another CA). *Name constraints* limit what names the CA
may certify at all: one restricted to `.corp.example.com` cannot produce a
working certificate for anything else, even if its key is stolen. Both are
baked in at creation and can't be changed afterwards.

Per-CA actions: **Copy Cert** (public, safe to share), **CRL** (the current
revocation list, showing its number and validity window), **Disable** (retire
it — it stops issuing but keeps publishing its CRL, which is almost always
what you want), and **Delete** (only possible if it never issued anything).

CA private keys are never shown anywhere in the UI or API — they exist only
to sign, server-side.

## Templates

Defines what a newly issued certificate looks like: key algorithm/size,
validity period, key usage, and extended key usage. Pick one when issuing
a certificate or signing a CSR.

## Renewing a certificate

Open a certificate pktCert issued and use **Renew Now**. You get a new
certificate and a **new private key** from the same CA and template — the old
key is never re-certified, because any compromise of it would carry straight
into the replacement.

The old certificate is marked **superseded**, not revoked. It stays valid so
the running service keeps working until someone installs the replacement.
Revoke it yourself once you have.

**Auto-renew** does the same automatically once a certificate comes within a
window you choose. It does *not* install anything — the new key still has to
be put on the server — so it removes the "nobody noticed it was expiring"
failure, not the deployment step.

## Approvals

Only relevant if an admin has turned on approval under Settings → Cert
Settings. When it's on, issuing or revoking records a request here instead of
happening immediately, and a **different** admin has to approve it. You can't
approve your own request; withdrawing it is always allowed.

When approval is off — the default — this page just says so, and issuing
works exactly as it always has.

## Alerts

Active/History/Rules tabs, same pattern as the rest of the pkt suite.

A rule watches one **condition**, and most conditions have settings of their
own so you decide what the limit is here: how many days before expiry, the
minimum key size you accept, which signature algorithms count as broken, how
long a validity period is too long. Alongside expiry and revocation there are
conditions for weak keys, weak signatures, self-signed certificates,
over-long validity, wildcards, issuers you don't control, newly discovered
certificates, a certificate changing on a host, a CA's CRL going stale, and
repeated failed device enrolments.

**Limit to** narrows a rule to part of the inventory — one source, a name or
host pattern. Worth using: a rule covering everything tends to get ignored.

Revocation alerts never auto-resolve (revocation is terminal); the others
clear automatically once the condition is no longer true.

## Letting devices enrol themselves

Devices that support **EST** (RFC 7030) — switches, routers, firewalls, VPN
clients — can request their own certificates instead of someone issuing one by
hand and copying files onto the box. The device generates its own key; pktCert
never sees it.

An admin creates an **enrolment profile** under Settings → Enrolment: a shared
secret bound to one CA and one template, optionally restricted to a name
suffix and to a maximum number of certificates. Point the device at
`https://this-server/.well-known/est/` and give it the profile's username and
secret.

The secret is shown once, when the profile is created. If it leaks, rotate
it — every device on the old secret stops enrolling immediately.

## Looking up an IP address

Where an IP shows up in the app (e.g. a scanned certificate's host),
lookups use your own per-user API keys under Settings → User Keys — same
pattern as the rest of the pkt suite.

A **?** button near most page headings and Settings sections opens a
short explainer.

For longer-form documentation, click **Documentation** in the sidebar
(just above your account info) — it opens this guide, the Administrator
Guide, and the PKI & Discovery guide as in-app tabs, so you don't need the
repo checked out to read them.
